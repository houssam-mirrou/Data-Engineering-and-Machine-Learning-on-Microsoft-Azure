02 / RÉSUMÉ EXÉCUTIF


Une chaîne Azure démontrée,
une mise en production à compléter
L’objectif est de construire, dans un contexte fintech, une chaîne de préparation et de modélisation de la
consommation électrique horaire. Azure Data Factory copie les données vers un stockage Azure à espace
de noms hiérarchique ; Azure Machine Learning assure l’exploration, le prétraitement, l’apprentissage et
l’évaluation.

Les captures confirment une copie ADF réussie, une forêt de régression dans Designer Classic, des
prédictions sur 29 074 observations et l’enregistrement de forecastingmodelv1, version 1. Un job
d’inférence est ensuite Completed dans un autre workspace. La disponibilité d’une API temps réel n’est pas
démontrée. [E29, E53–E55, E61–E64]

03 / INTRODUCTION ET CONTEXTE MÉTIER


Prévoir la consommation,
structurer un flux traçable
Le rôle de Data Developer en fintech conduit ici à traiter une série énergétique comme cas d’usage de
pipeline de données et de Machine Learning. Une prévision peut contribuer à une analyse de risque ou à
une simulation d’exposition énergétique ; aucun bénéfice financier ni usage métier en production n’a été
mesuré dans ce projet.

La cible PJME_MW représente une puissance électrique agrégée, exprimée en mégawatts. Malgré le terme
« consommation » du sujet, il ne s’agit pas directement d’une énergie en MWh. Datetime situe l’observation
horaire. Le modèle démontré apprend essentiellement les régularités calendaires de cette série.

Decision Forest Regression

Le modèle effectivement visible est Decision Forest Regression. Il est connecté à Train Model, qui reçoit le
jeu d’apprentissage après sélection des colonnes. Le modèle entraîné et le jeu de test convergent ensuite
vers Score Model ; sa sortie alimente Evaluate Model. [E50–E54]




Figure 7 — Connexion de la forêt de régression à Train Model · E50. Recadrage de la capture originale.

Une forêt de régression combine plusieurs arbres pour approximer des relations non linéaires et leurs
interactions. Ce choix convient à une première modélisation de la saisonnalité calendaire. Il ne représente
pas explicitement la dynamique séquentielle : aucune valeur retardée de consommation ni statistique
glissante n’est visible dans les variables de test.

15 / Conclusion et perspectives
Le projet établit une base fonctionnelle de Data Engineering et de Machine Learning sur Azure : ingestion
réussie, organisation du stockage, exploration des données, chaîne Classic de régression, évaluation
disponible, enregistrement de modèle et exécution d’un job d’inférence. Le résultat évalué reste modéré,
avec une erreur absolue moyenne de 3 177,774545 MW.

La robustesse de la prévision et l’exploitabilité du système exigent encore un audit de la coupe temporelle
du run Classic, une filiation complète entre les assets et les workspaces, ainsi qu’une validation du contrat
d’inférence. Le modèle peut être amélioré par des variables historiques et externes, puis comparé à des
références temporelles simples.


   Priorités de finalisation
   1. Exporter le pipeline, le code embarqué et l’audit train/test.
   2. Identifier le datastore réellement utilisé par chaque asset.
   3. Valider les baselines et l’inférence sur des entrées futures sans cible.
   4. Déployer et tester un endpoint, puis automatiser et superviser le flux.
